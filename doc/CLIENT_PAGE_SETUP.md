# Клиентская страница обзвона ("/") — настройка

Публичная страница по корневому адресу (`https://<frontend-domain>/`, вне
`/admin_panel_2026`): вход через Google (любой аккаунт, без ограничения по
списку email), список номеров для обзвона, генерация озвучки, запуск обзвона
и лог звонков со статусами.

Это отдельный контур авторизации от админки — токен клиента (`role: 'client'`)
не даёт доступа к admin-эндпоинтам и наоборот, и хранится в `localStorage`
под другим ключом (`client_token`), так что можно быть залогинен в обе
страницы одновременно в одном браузере.

---

## 1. Настройка Google-логина для клиентской страницы

Используется **тот же** `GOOGLE_CLIENT_ID`, что и для входа в админку (см.
основной README, раздел "Настройка входа через Gmail"). Единственное отличие:
в Google Cloud Console → **Authorized JavaScript origins** нужно убедиться,
что там указан именно домен фронтенда целиком (`https://<frontend>.vercel.app`),
а не какой-то конкретный путь — подходит и для `/admin_panel_2026`, и для `/`,
поскольку origin проверяется без учёта пути.

**Важно:** в отличие от админского Google-логина, здесь **нет** проверки по
`ALLOWED_GMAIL_EMAILS` — войти может любой аккаунт с подтверждённым email.
Изоляция данных между разными клиентами обеспечивается тем, что каждая
запись (номера, озвучки, кампании, лог звонков) хранится с полем
`ownerEmail`, взятым из токена, а не общим списком на всех.

## 2. Что видно на странице

1. **Таблица номеров** — добавление (валидация `+380XXXXXXXXX`) и удаление.
2. **Текст + голос** — textarea, выбор голоса ElevenLabs, кнопки **"Озвучить"**
   (генерация через тот же пайплайн ElevenLabs → Vercel Blob, что и в
   админке, но результат виден только этому клиенту) и **"Прослушать"**
   (воспроизведение уже сгенерированного файла).
3. **"Обзвонить"** — три режима:
   - **Сейчас** — обзванивает весь список номеров немедленно, в рамках того
     же запроса.
   - **Сегодня в HH:MM** — создаёт отложенную кампанию, её подхватит cron.
   - **Каждые N минут** — создаёт периодическую кампанию.
4. **Лог звонков** — номер, время начала (когда трубку подняли), длительность
   (живой счётчик, пока звонок не завершён), статус.

## 3. КРИТИЧЕСКИ ВАЖНО: расписание "Сегодня в HH:MM" и "Каждые N минут" зависят от cron

Режим "Сейчас" работает сразу же и не требует ничего дополнительного.
Но режимы **"Сегодня в HH:MM"** и **"Каждые N минут"** реально сработают
только тогда, когда что-то дёрнет `GET /api/cron/dispatch-campaigns` — сами по
себе они просто создают запись в БД со временем следующего запуска
(`nextRunAt`) и ждут.

### Вариант A — pg_cron + pg_net (рекомендуется — минутная точность, не зависит от тарифа Vercel)

Supabase Postgres умеет сам, изнутри базы, каждую минуту дёргать бэкенд —
через связку расширений **pg_cron** (планировщик задач в самой БД) и
**pg_net** (асинхронный HTTP-клиент из SQL). Это единственный вариант,
который даёт настоящую минутную точность независимо от того, на каком
тарифе Vercel развёрнут бэкенд — триггер идёт от Supabase, а не от Vercel.

Готовый скрипт — `backend/sql/pg_cron_dispatch_campaigns.sql`. Порядок:

1. В Supabase Dashboard → **Database → Extensions** включить `pg_cron` и `pg_net` (если у используемой роли достаточно прав, можно и через `CREATE EXTENSION` из самого скрипта).
2. Открыть **SQL Editor**, вставить содержимое `pg_cron_dispatch_campaigns.sql`.
3. Заменить `<BACKEND_URL>` на реальный домен бэкенда и `<CRON_SECRET>` — на значение из `backend/.env`.
4. Выполнить — job зарегистрируется и с этого момента будет запускаться каждую минуту (`* * * * *`).

Проверить, что всё работает: `select * from cron.job_run_details order by start_time desc limit 20;` — там видно каждый запуск и статус. Ответы самих HTTP-запросов (что вернул бэкенд) — в `net._http_response`.

Приостановить без удаления: `select cron.unschedule('dispatch-client-campaigns');`.

### Вариант B — Vercel Cron (проще всего для быстрого старта, но с оговоркой)

В `backend/vercel.json` уже добавлена конфигурация:
```json
"crons": [{ "path": "/api/cron/dispatch-campaigns", "schedule": "*/5 * * * *" }]
```
**Проблема:** расписание чаще одного раза в день (`*/5 * * * *` — это каждые
5 минут) поддерживается только на платном плане **Vercel Pro**. На **Vercel
Hobby** Cron Jobs ограничены одним запуском в сутки — с такой частотой
"Каждые N минут" и точное "Сегодня в HH:MM" по факту работать не будут
(кампания подхватится максимум раз в день). Если у вас Vercel Pro — этот
вариант проще pg_cron и ничего дополнительно настраивать в Supabase не нужно.

### Вариант C — внешний пингер (запасной, если pg_cron недоступен)

Для минутной точности без Vercel Pro и без настройки pg_cron можно
использовать бесплатный внешний cron-сервис (например
[cron-job.org](https://cron-job.org)), настроив его дёргать:
```
GET https://<backend-domain>.vercel.app/api/cron/dispatch-campaigns
```
раз в 1–5 минут. Менее надёжно, чем pg_cron (зависит от аптайма стороннего
сервиса), но не требует прав на расширения БД.

### Защита эндпоинта

Задайте `CRON_SECRET` в `.env` — тогда эндпоинт примет запрос только с:
- заголовком `x-cron-secret: <CRON_SECRET>` — именно так его передаёт скрипт `pg_cron_dispatch_campaigns.sql` (вариант A) и большинство внешних пингеров (вариант C, включая cron-job.org на бесплатном тарифе);
- или заголовком `Authorization: Bearer <CRON_SECRET>` — это ставит **сам** Vercel Cron автоматически, если переменная `CRON_SECRET` задана в проекте (вариант B), ничего дополнительно настраивать не нужно.

Если `CRON_SECRET` не задан — эндпоинт открыт всем. Это осознанное
упрощение для быстрого старта, но для продакшена `CRON_SECRET` обязателен,
иначе кто угодно может дёргать чужие кампании досрочно.

## 4. Ограничение по звонкам — то же, что и в остальном проекте

Обзвон с клиентской страницы использует ту же логику, что тестовый звонок в
админке (`CallsService`) — то есть звонки идут **только** через активные
номера Telnyx (см. `doc/DIDWW_SETUP.md` / `doc/DIDLOGIC_SETUP.md` про то,
почему DIDWW/DIDLogic номера для звонков пока не годятся). Если в пуле нет ни
одного активного Telnyx-номера — кампания создастся, но каждый звонок в ней
завершится ошибкой в логе.

## 5. Данные и приватность

Каждый Google-аккаунт видит только свои номера, свои озвучки, свои кампании
и свой лог звонков (`ownerEmail` фильтрует всё на уровне бэкенда, а не
только на фронтенде). Изоляция от админки полная: админские тестовые
звонки/озвучки хранятся с `ownerEmail: null` и не показываются ни одному
клиенту, а клиентские записи не показываются в админке.
